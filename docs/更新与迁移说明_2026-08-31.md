## 2. 本次要解决的问题

玩家收集到 25 张怪物卡后，收藏家腰带没有明显属性变化，原因包括：

1. 卡片拾取只更新 `MonsterBook` 内存数据，没有触发角色有效属性重算。
2. 收藏统计原本只查询数据库；当前角色的卡片要等自动保存后才会写入数据库。
3. 收藏统计有 30 秒缓存，刚达到奖励档位时可能继续读取旧值。
4. 收藏家 NPC 原本只显示简短的固定信息，玩家无法快速确认腰带是否装备、当前档位和实际加成。
5. v83 客户端装备 Tooltip 使用静态 WZ 数据，不会自动显示装备实例的动态属性来源。
6. 账号内多个角色的卡片、任务和未保存进度没有统一的实时统计来源。
7. 卡片保存和收藏读取缺少一致的并发与数据库异常处理。

## 3. 服务端代码更新

### 3.1 收藏统计和缓存

文件：`gms-server/src/main/java/org/gms/server/CollectionService.java`

- 保留账号级统计：账号内所有角色的怪物卡数量累计。
- 每种怪物卡最多计入 5 张。
- 使用统一的账号收藏快照：
  - 数据库读取离线角色数据；
  - 所有在线角色使用内存中的最新卡片和已完成任务；
  - 当前角色尚未保存的进度直接纳入；
  - 数据库与在线内存数据不会重复计算。
- 同一种怪物卡在账号范围内统一封顶 5 张，而不是每个角色分别封顶。
- 收藏快照按在线角色集合缓存；卡片或任务状态变化后立即失效。
- 数据库读取失败时不再把零值当作成功结果；有最近有效快照时保留并标记为旧数据，没有可用快照时向玩家显示数据暂不可用。
- 收藏摘要只读取一次统一快照，避免卡片、任务和奖励分别查询造成重复数据库访问。
- 收藏进度变化后刷新账号内所有世界的在线角色。
- 新增统一收藏摘要格式，供命令、NPC、里程碑提示和装备状态提示复用。
- 摘要必须显示：
  - 收藏家腰带装备状态；
  - 账号共享说明；
  - 当前怪物卡数量、已解锁档位、距离下一档数量；
  - 当前任务数量、已解锁档位、距离下一档数量；
  - 全属性、物攻、魔攻、HP、MP 加成。

奖励规则保持不变：

- 每累计 25 张卡片：力量、敏捷、智力、运气各 `+1`。
- 每累计 50 个已完成任务：全属性各 `+1`、物攻 `+1`、魔攻 `+1`、HP/MP 各 `+100`。
- 以上加成只有在装备 `1132991` 收藏家腰带时才计入角色有效属性。

### 3.2 账号共享腰带升级

- 腰带等级由收藏快照实时计算，不新增重复的装备实例属性。
- 卡片奖励档位为 `cards / 25`，任务奖励档位为 `quests / 50`。
- 收藏家腰带等级 = 卡片奖励档位 + 任务奖励档位。
- 账号内所有收藏家腰带都使用同一个账号等级和收藏属性，不会因角色或腰带实例不同而产生差异。
- 当前等级是收藏成长记录和展示层级，现有卡片/任务属性奖励保持原规则，不额外重复叠加。
- 如果未来增加材料、金币或实体腰带外观升级，应另行设计实例替换和客户端 WZ 同步，不与本次账号等级混用。

### 3.3 卡片拾取即时刷新

文件：`gms-server/src/main/java/org/gms/client/MonsterBook.java`

- 使用拾取前后的账号收藏快照比较卡片奖励档位。
- 卡片数量实际增加时：
  1. 清理账号收藏缓存；
  2. 刷新账号内所有在线角色的收藏家腰带属性；
  3. 比较账号总卡片档位是否跨过 25 的倍数；
  4. 跨档时弹出收藏里程碑摘要。
- 已达到同一种卡片 5 张上限时，不重复增加数量、不重复刷新奖励。
- `getCards()` 返回快照，避免封装外遍历可变的 `LinkedHashMap`。
- `saveCards()` 先在锁内复制快照，再执行 JDBC batch，避免自动保存与拾取并发修改同一张表。

### 3.4 任务完成即时刷新

文件：`gms-server/src/main/java/org/gms/client/Character.java`

- 角色内存中的已完成任务会纳入收藏快照。
- 任务从未完成变为已完成，或从已完成重置为未完成时，立即失效账号快照。
- 账号内所有在线且装备收藏家腰带的角色都会重新计算属性。
- 跨过 50、100 等任务奖励档位时弹出任务里程碑摘要。
- 当前仍按不同任务 ID 统计；同一个可重复任务多次完成只计一个任务，后续如需改为完成次数应单独调整规则。

### 4.1 迁移执行方式

服务端启动时由 Flyway 自动执行未完成迁移。另一台机器执行前：

1. 确认数据库连接配置正确；
2. 确认数据库用户具有 Flyway 所需权限；
3. 启动服务端一次，让 Flyway 执行未完成的 `V1.11.53` 和 `V1.11.54`；
4. 重启或重新加载命令，使 `command_info` 中的新命令注册到内存。

可以用以下 SQL 验证：

```sql
SELECT installed_rank, version, description, success
FROM flyway_schema_history
WHERE version IN ('1.11.53', '1.11.54')
ORDER BY installed_rank;

SELECT syntax, level, enabled, clazz, default_level
FROM command_info
WHERE syntax IN ('collection', 'collect');
```

预期结果：

- `flyway_schema_history` 中存在版本 `1.11.53`、`1.11.54` 且 `success = 1`；
- `collection` 和 `collect` 各有一条启用记录；
- 两条记录的 `clazz` 为 `CollectionCommand`，`default_level` 为 `0`。

如果输入命令提示未知命令，优先检查迁移是否执行、`command_info.enabled` 是否为 1，以及服务端是否已重启。
